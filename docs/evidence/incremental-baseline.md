# 增量审计地基 · 基线

> 日期：2026-10-18
> 范围：diff 解析 + 函数级映射（选题 A 的第 1、2 环）
> 结论：**160 个合成单函数改动，选择准确率 160/160，平均审计量减少 91.5%。**

---

## 1. 已实现的三个模块

| 模块 | 文件 | 职责 |
|---|---|---|
| diff 解析 | `backend/app/services/incremental/diff_parser.py` | 从 unified diff 提取新文件行号区间；纯删除按锚点行处理；删除文件/二进制跳过 |
| 函数映射 | `backend/app/services/incremental/mapper.py` | 行区间 ∩ 函数区间 → 变更函数；同文件未变更函数作为"影响面提示"；无函数命中时回退整文件 |
| 基准脚本 | `docs/evidence/run_incremental.py` | 对语料注入单行改动，验证选择结果 |

设计上的两个明确选择：

1. **只做语法映射，不猜调用图**。跨合约影响需要调用图，标为"未分析"，而不是用启发式假装分析过。
2. **diff 没碰到任何函数时回退整文件**。改状态变量、import、修饰器都可能影响所有函数，这时"只审改动"是错的。

## 2. 基准结果

语料：`corpus/` 中 120 个合约文件（排除 SmartBugs 与测试文件），每个文件取前 2 个函数注入单行改动。

| 指标 | 值 |
|---|---|
| 用例数 | 160 |
| 恰好选中目标函数 | **160 / 160（100%）** |
| 平均选中函数数 | 1.0 |
| 平均文件函数数 | 11.76 |
| 平均审计量减少 | **91.5%** |

复现：

```powershell
python docs\evidence\run_incremental.py
```

---

## 3. 这个数字能说明什么、不能说明什么

**能说明**：给定 diff 行号，映射到函数这一步没有算术错误；单函数改动的场景下，增量选择确实能把审计量压到 1/12 左右。

**不能说明**：

| 不能声称 | 原因 |
|---|---|
| "真实 git diff 也行" | 基准里是合成 diff，只有一行、无上下文；真实 diff 有 context、可能跨函数、跨文件、带重命名 |
| "91.5% 是真实节省" | 取决于改动粒度。真实提交经常一次改多个函数，节省会显著低于 91.5% |
| "影响面分析完成了" | 只提示同文件未变更函数；跨文件/调用图明确未做 |
| "增量审计质量更好" | 这里只测"选得对不对"，没测"漏没漏"——漏审的代价需要另一套实验（改 A 影响 B） |

第 4 条尤其重要：**增量审计最大的风险不是多审，是少审**。一次改动可能破坏另一个未被选中的函数，当前实现不会发现。这个限制必须写进论文的"不足与展望"。
