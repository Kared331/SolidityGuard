# 6A 覆盖可核算性 · 实验结果

> 日期：2026-10-18
> 实验脚本：[`run_6a.py`](run_6a.py)（确定性，不调用外部 API）
> 结论：**4 类故障 × 100 次注入，全部被账本标记（CP 95% 下界 0.9705）；20 个合约的账本单元数与提取数完全一致。**

---

## 1. 命题

> 对任意一次审计运行，每个被提取的函数都恰好落在
> `audited / skipped / failed / filtered` 之一，原因是可读的；
> 只要有任何一个函数没有被审计，运行就必须被标记为 `degraded`。

这不是"检测质量"命题，而是"系统是否说谎"命题。它可以用故障注入严格检验，不依赖模型能力。

---

## 2. 方法

| 项 | 设计 |
|---|---|
| 故障类 | `budget`（预算耗尽）、`rag_failure`（检索异常）、`llm_error`（调用抛错）、`parse_error`（响应不可解析） |
| 注入次数 | 每类 **100** 次，共 400 次 |
| 随机化 | 每次随机抽 1–3 个合约（fixture + corpus 中 ≤12 单元的合约）、随机种子 |
| 判定 | 该类故障必须在账本里留下对应 `reason`、对应计数器、且 `degraded=true`；恒等式成立；所有单元状态合法 |
| 外部依赖 | LLM / embedding / Chroma 全部替换为确定性桩（故障注入需要可复现；真实模型单独有 [`first-real-llm-run.md`](first-real-llm-run.md)） |
| 统计 | Clopper–Pearson 单侧 95% 下界 |

**为什么用桩**：如果把真实模型放进故障注入，每次运行的行为不可复现，就分不清"没标记"是系统缺陷还是模型输出波动。桩保证故障是唯一变量。

---

## 3. 结果

| 故障类 | 注入 | 被标记 | 标记率 | CP 95% 下界 |
|---|---|---|---|---|
| budget | 100 | 100 | 100% | **0.9705** |
| rag_failure | 100 | 100 | 100% | **0.9705** |
| llm_error | 100 | 100 | 100% | **0.9705** |
| parse_error | 100 | 100 | 100% | **0.9705** |

计分规则（任一项不满足即判"未标记"）：

- 恒等式 `extracted = audited + skipped + failed + filtered` 成立；
- 所有单元 `status ∈ {audited, skipped, failed, filtered}`；
- 所有非 audited 单元都带 `reason`；
- 对应计数器 > 0 且 `degraded = true`。

复现：

```powershell
python docs\evidence\run_6a.py --n 100
```

---

## 4. 单元守恒（20 个合约）

对 corpus 中 20 个合约（不注入故障，LLM 桩返回 `[]`）：

- 账本 `functions_extracted` **等于** `extract_functions()` 的单元数；
- 每个合约都满足四项恒等式；
- 失配：**0**。

这证明的是"**从提取到入账没有丢失**"，不是"提取等于 Solidity AST 真值"。后者是 P0 的工作（176 个文件、参考扫描器对比，漏/噪 0）。两者合起来才构成覆盖率的证据链，但**两步都是我们自己的实现**，不是 solc AST 交叉验证——这一点必须在声明里写清楚。

---

## 5. 这次实验证明了什么

| 能声明 | 依据 |
|---|---|
| 四类基础设施故障不会静默 | 400 次注入，100% 标记，CP 下界 0.9705 |
| 每个函数都有明确归宿 | 恒等式 + 状态集合检查，400/400 |
| 预算耗尽不再表现为"0 漏洞" | `skipped/budget` + `degraded` |
| 检索故障不影响覆盖率统计 | `rag_failures` 与 `audited` 解耦，实测两者同时成立 |

## 6. 不能声明什么

| 不能声明 | 原因 |
|---|---|
| "覆盖率等于 AST 真值" | 只与自己的提取器对比；参考扫描器也是自研 |
| "模型审计质量" | 全部用桩；真实模型证据只有 1 个合约（见 first-real-llm-run） |
| "并发下也无竞态" | 文件级线程池未注入并发故障（同一合约多文件并行时的计数器竞争未测） |
| "所有故障类都覆盖" | 只测了 4 类；磁盘满、DB 写入失败、Redis 不可用未注入 |

## 8. 回归

`tests/test_coverage_accounting.py`（5 条）直接 import 实验脚本，跑小规模版本：

- 4 类故障各 3 次，必须全部标记；
- 3 个合约的账本单元数必须等于提取数，四项恒等式成立。

这样实验脚本改了但逻辑退化时，单测会红，不需要每次跑 400 次。
